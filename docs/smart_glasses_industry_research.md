# スマートグラスのiOSコンパニオンアプリ動作モデル調査レポート

本ドキュメントは、Meta (Ray-Ban Meta)、Solos (AirGo)、Even Realities (Even G1/G2) などの主要スマートグラスにおける、iOSアプリのバックグラウンド動作とハードウェア連携の設計パターンの調査結果です。

---

## 1. コンパニオンアプリの立ち位置と制約

スマートグラス製品におけるiOSコンパニオンアプリの基本的な役割は **「バックグラウンド中継（Brain）」** です。スマホをポケットに入れたまま、グラス本体の操作で処理を完結させるため、iOSの厳しいバックグラウンド制限と連携する設計が採用されています。

### iOSにおけるバックグラウンド動作の技術仕様

| 設計要素 | 動作仕様 / 技術的アプローチ | 影響と対策 |
| :--- | :--- | :--- |
| **アプリの常駐状態** | ユーザーによるフォースクローズ（マルチタスク画面でのスワイプ終了）をされない限り、バックグラウンドに常駐。 | アプリを終了すると、スマートグラスとのBluetooth/BLE通信リンクが即座に切断され、AI機能や通知連携が停止します。 |
| **接続維持方法** | **CoreBluetooth / BLE State Restoration**。iOSがメモリ不足などでアプリをサスペンド・終了しても、スマートグラス側からデータが送られてくると、OSがアプリをバックグラウンドで自動復帰（Wakeup）させます。 | XcodeのCapabilitiesにて `Background Modes` の `Uses Bluetooth Central accessories` を有効にすることが必須です。 |
| **音声・ストリーミング維持** | **Background Audio**。グラス側からのマイク音声受信やスピーカーへの音声送信時、オーディオセッションをアクティブにしてOSによるサスペンドを防ぎます。 | `Background Modes` の `Audio, AirPlay, and Picture in Picture` を有効にし、ストリーミング中にオーディオセッションを維持します。 |
| **OSによるペナルティ回避** | iOSは長時間の不要なバックグラウンド処理を検知するとアプリを強制終了（Watchdog）します。そのため、**処理時のみオンデマンドで処理を動かす**設計が最適です。 | 常時WebSocket接続や常時ポーリングを避け、グラス側からのトリガー発火時のみ通信をアクティブにする設計（今回のオンデマンド実装）が推奨されます。 |

## 2. 他社製品の動作・トリガーモデル比較

各スマートグラス製品が採用している、スマホをポケットに入れた状態（Background）での対話起動・アクションモデルは以下の通りです。

### A. Meta AI (Ray-Ban Meta)
*   **起動トリガー**: オンボード（グラス内蔵チップ）での音声検知（「Hey Meta」）またはフレーム上の撮影ボタン押下。
*   **通信フロー**:
    1.  グラスが「Hey Meta」を検知すると、自動的にBluetoothオーディオセッション（HFP/A2DP）をアクティブにしてスマホと接続。
    2.  バックグラウンドで動作している「Meta View」アプリを介して、Metaのクラウドサーバーにクエリを送信。
    3.  応答された音声をスマートグラスのスピーカーから再生。
*   **特徴**: iOSアプリが画面上に開いていなくても、バックグラウンドでプロセスが稼働していれば音声のみで完結。

### B. Solos AirGo (Solos Smart Glasses)
*   **起動トリガー**: テンプル（つる）の部分に搭載された **物理タッチセンサー（スマートボタン）**。
*   **通信フロー**:
    1.  ユーザーがテンプルをタップまたはスワイプ。
    2.  Bluetooth経由で「Solos AirGo」アプリにイベントが通知される。
    3.  アプリはバックグラウンド状態のまま、SolosChat (AIアシスタント) を起動してマイク音声の入力を受け付け、サーバーに送信。
*   **特徴**: ユーザーが意図的にボタンを押して開始・終了を明示するトグル方式。今回のスマートグラスゲートウェイで実装した「音量キー/物理ボタンによるトグル方式」と非常に近い設計。

### C. Even Realities G1 (Even Realities)
*   **起動トリガー**: テンプルのタッチ操作、または **IMU（ジャイロ・加速度）を用いたヘッドジェスチャー**（例：うなずく、上を向くなど）。
*   **通信フロー**:
    1.  ユーザーが特定のジェスチャーやタップを行う。
    2.  グラスのセンサーからBLE経由でアプリにイベントを伝達。
    3.  アプリ（バックグラウンド）がナビゲーションやリアルタイム翻訳、AIアシスタントの処理をキック。
*   **特徴**: ディスプレイ付きグラスであるため、iOSアプリがバックグラウンドでGPS情報を取得し続け、ナビゲーション画面をグラス側にレンダリングして転送する。

## 3. 本プロジェクトへの示唆・最適設計のまとめ

他社製品のベストプラクティスをふまえ、今回実装した **「iOSアプリ＝設定画面 ＋ バックグラウンド中継器」** の設計は、iOSのシステム制約に最も適しています。

1.  **オンデマンド通信の正当性**:
    *   他社アプリ（Even Realities等）でも、バックグラウンドで常時大量の通信を行うとiOSの省電力機能（Low Power ModeやHeuristics）によって即座に休止・強制終了されるリスクが高まります。
    *   グラス側の操作（音量キーなど）を起点とし、その瞬間だけWebSocket接続を張ってGemini処理を行う設計は、**OSからキルされにくく、iPhoneのバッテリー消費を極小化する観点から最も堅牢**です。
2.  **実機導入時の注意点**:
    *   iPhone側の設定で **「Appのバックグラウンド更新 (Background App Refresh)」** を必ずオンにする必要があります。
    *   iPhoneが「低電力モード」に入っている場合は、バックグラウンドのBluetoothイベント受信がOSによって一時的に制限・遅延されるため、実運用時は低電力モードの解除が推奨されます。
