# 2. GCP Agent Platform と拡張ツールのアーキテクチャ方針

- **ステータス**: Accepted
- **日付**: 2026-06-06
- **起案者**: Antigravity

## 文脈 (Context)

スマートグラス (Ray-Ban Meta) を用いたリアルタイム対話型AIエージェント (Personal Context Engine) において、以下の要件を満たすプラットフォーム選定と拡張（Tools/MCP）のアーキテクチャ設計が必要となった：
1. **リアルタイム双方向コミュニケーション**: 音声・映像の超低遅延双方向対話（Speech-to-Speech）を実現する。
2. **高い拡張性**: 後から多様な外部ツール（MCPサーバーやカスタム機能）を容易に追加・拡張できるようにする。
3. **セキュリティと保守性**: クラウドサービスとしてのセキュリティ基準を満たしつつ、コンポーネントごとの責務を明確にし、バックエンド中継サーバーの肥大化を防ぐ。

## 決定 (Decision)

### 1. エージェントプラットフォームの選定
* **Vertex AI Agent Builder / Agent Platform (マネージドエージェント)** を中央のオーケストレーションハブとして採用する。
* コアモデルには、Vertex AI上でGemini Live API (WebSocket) に対応した双方向コミュニケーションモデル（例: `gemini-2.0-flash` 等）を使用する。

### 2. 拡張ツール (Tools / MCP) の構成とデプロイ
* 後からエージェントを拡張するためのツール（MCPサーバー等）は、すべて **FastAPI 等のWebフレームワークを用いて HTTP REST API（OpenAPI）化** して開発する。
* 実装されたツールは **Google Cloud Run** 等のコンテナ実行環境に個別デプロイする。
* 各ツールの OpenAPI 仕様書 (Swagger) を用いて、Vertex AI Agent Builder の **Extensions (拡張機能)** としてエージェントに直接登録・紐付ける。

### 3. セキュリティと認証
* Google Cloud Run にデプロイされたツールへのアクセス制御には、Google Cloud の IAM 認証（OIDC トークン認証）を利用する。
* Vertex AI Agent Builder の呼び出し元サービスアカウントに対して、各 Cloud Run サービスの呼び出し権限 (roles/run.invoker) を最小限の特権原則で付与し、セキュアなサービス間通信を担保する。

### 4. FastAPI バックエンド中継サーバーの責務の限定
* FastAPI 中継サーバーは、スマートグラス (iOS エッジゲートウェイ) と Vertex AI Agent Platform の WebSocket セッションを仲介する「中継プロキシ」に特化する。
* **中継プロキシを維持する理由（iOSからの直接接続を行わない理由）**:
  * **セキュリティ保護**: GCP のサービスアカウントキーや高度な認証情報を iOS クライアント（スマートグラスのゲートウェイ）に直接持たせることを避け、漏洩リスクを完全に排除する。
  * **疎結合性の維持**: 接続先モデルや GCP 認証仕様の変更時に iOS アプリのアップデート（ストア審査等）を不要にし、サーバー側の設定変更のみで対応可能とする。
  * **ロギングと監視**: 接続品質（ミリ秒単位のレイテンシ）やトークン消費量のログを一元的に収集・監視しやすくする。
* ツールの実行ロジックや MCP クライアントとしての呼び出しロジックは中継サーバー内には実装せず、Vertex AI の Extensions 機構に完全に委ねる。これにより、中継サーバーのコードをシンプルかつ堅牢に保つ。

## 結果 (Consequences)

* **メリット**:
  * **セキュリティの向上**: iOS クライアント側に機密性の高い GCP 認証情報（サービスアカウントなど）を保持する必要がなくなる。
  * エージェントの挙動や使用するツールの管理が GCP コンソール（Vertex AI Agent Builder）側で一元化され、運用性が向上する。
  * 新しいツールを追加する際、中継サーバーのコードを変更・再デプロイすることなく、新規 API を Cloud Run にデプロイして Extensions に追加するだけで拡張が可能となる。
  * IAM 認証を利用したマネージドなサービス間認証により、API キーなどのシークレット管理の手間とリスクが削減される。
* **デメリット/トレードオフ**:
  * ローカルの標準的な MCP サーバー（stdio 等）を直接利用する場合と比較して、Web API（FastAPI 等）へのラッピングと Cloud Run へのデプロイというオーバーヘッドが発生する。
